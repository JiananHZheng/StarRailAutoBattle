# 行动轴头像知识库与识别工具（开发阶段）

目标：建立《崩坏：星穹铁道》3.0 版本至今的行动轴头像知识库，并用一个**不调用大模型**的本地工具识别截图或视频中的行动轴。当前只识别行动轴上的单位头像，包括角色、角色召唤物（含忆灵）、怪物和怪物召唤物；不做技能、伤害、血条识别，也不控制战斗。

## 组成

| 位置 | 作用 |
| --- | --- |
| `src/AxisRecognizer.Core/` | 识别库：知识库读写、相对坐标布局、头像特征、识别、序列分析、文本结果。`Recognizer.Recognize(Mat)` 是日后自动截图程序的调用入口 |
| `src/AxisTool/` | 开发用命令行工具 `axis`：建库、标定、标注、盲测、纠正、视频取帧、`axis record` 录制 |
| `src/VideoRecorder/` | B 站录制核心：在独立的 WebView2 窗口里未登录播放并截取画面（启动器视频页和 `axis record` 共用） |
| `tests/AxisRecognizer.Tests/` | 用合成画面做的自动测试（不含任何游戏图像） |
| `axis-data/`（不进 Git） | 本地数据：`kb/` 知识库、`runs/` 盲测记录、`recordings/` 开发录制、`video-runs/` 启动器视频页的运行、`inbox/` 待处理的截图和视频 |

技术：.NET 10 + OpenCvSharp 4.13（自带 FFmpeg 解码，可读取本地 mp4/mkv 等视频）+ Microsoft Edge WebView2（录制）。本机没有 Python、ffmpeg、yt-dlp，工具不依赖它们，也**不下载原视频文件**：链接只通过播放并截取窗口画面来录制（用户 2026-10-27 规则：只在本地算法沙箱内使用，不算转载）。

## 知识库结构（`axis-data/kb/`）

| 文件 | 内容 |
| --- | --- |
| `kb.json` | 版本号与识别参数（阈值、特征权重） |
| `units.json` / `units.txt` | 单位登记表（相当于“单位”表）。**每种行动轴头像一个全局编号 `U0001`…**，不分角色、召唤物、怪物；类型和名称只是注释，由用户补充。旧编号（`CH-爻光`、`M0003` 等，2026-10-27 前使用）保留为别名，仍可使用。内置 `EMPTY` 表示空格 |
| `screenshots.json` + `screenshots/` | 原始截图（用户截图保存为 PNG；来自视频的帧保存为 JPEG，知识库 v58 起，旧的用 `axis kb jpeg-frames` 转换过），记录来源、许可、访问时间、游戏版本、用途（train 用于建库，holdout 只用于检验）和各格的正确答案 |
| `samples.json` + `samples/<单位>/` | 从截图裁出的独立头像样本：所属单位、来源截图与格位、相对坐标、标注来源（`user` 或 `claude-assisted`）、确认状态、加入时的知识库版本 |
| `layouts.json` | 行动轴布局（按宽高比区分），坐标以游戏画面高度归一并以左上角为原点，不写死像素 |
| `cues.json` + `cues/<线索>/<标签>/` | 行动轴头像以外的画面线索样本（知识库 v93 起）：当前格左侧标记（`marker`）和右下角状态文字（`phase-text`）的裁剪、标签、来源和标注来源；见下方“画面线索” |
| `changelog.md` | 每次改动一条，写明新增了什么、标签来源和内容校验值 |
| `corrections.log` | 盲测中的每一次误识别（原始输出、正确答案、工具候选、当时的知识库版本） |

除四类单位外，还有两类条目（由用户说明确定）：
- `MKnnn` **非单位提醒条目**：例如行动值 999 的“特殊时刻提醒”。工具会识别它，但不写入结果，也不算行动。
- `ATnnn` **附属格**：属于上一条目的一部分，例如阿哈时刻下方的四人头像格（阿哈时刻附加行动）。结果中写成“阿哈时刻（含阿哈时刻附加行动）”，两者算一次行动。

单位类型可以用 `axis kb unit rename --id 编号 --kind 新类型` 更正，编号保持不变。

规则：
- 同一头像 = 同一编号，即使场上有多个实体（例如两只相同的怪物）；不同头像 = 不同编号。拿不准是否同一单位时先分别编号并标“疑似”，经你确认后再合并（`axis kb unit merge`，旧编号保留为别名）。
- 知识库按“表”组织：单位（`units.json`）、截图（`screenshots.json`）、样本（`samples.json`，每个样本指向单位和来源截图）、布局；每次运行的逐格识别记录在该运行的 `raw_detail.tsv`（相当于“出现记录”表）。
- 名称未经核实时标为 `candidate`，结果里会显示“（名称待确认）”。
- 网络图片只有在核实许可允许本地保存时才能加入（`--source-type web` 必须带 `--license`），否则只记录链接。
- 新样本与同一单位已有样本几乎相同时不重复保存（去重）。`axis kb stats` 会显示磁盘占用（上限 2 GB）。

## 识别方法（v0.1）

1. 去掉画面四周的纯黑边（视频的黑边或截图的边框），得到游戏画面区域。
2. 按宽高比选择已标定的布局，把每格的相对坐标换算成像素。
3. 每格在小范围内试位移和缩放（±6%），取与知识库最匹配的裁剪。
4. 特征：去掉格子边缘后，计算灰度相关、边缘强度相关和色调/饱和度直方图交集，三者加权求和。
5. 最高分 ≥ 0.80，且比第二名高出 ≥ 0.03 时，才给出确定答案；否则输出“未知/待确认”，附上分数 ≥ 0.50 的工具候选。

所有参数都在 `kb.json` 中，修改会记入 changelog。在合成画面上，单帧识别约 40–60 ms。

**判断空格：** 学到的“空格外观”无法推广到任意战斗背景（自动测试已证实）。因此现在不会把低分格当作空格隐去：宁可显示“未知/待确认”，也不让新单位消失。拿到真实截图后，再根据格子边框等结构特征来判断有无头像，或调整 `EmptyBelowScore`。

### 模糊识别（知识库 v42 起）

为了把同一单位的不同状态（如加速后整体变红）归为同一编号，比较方式改为：灰度 0.4 + 边缘 0.6，**不再使用颜色直方图**（状态变色会改变颜色），特征尺寸 32。确定阈值 0.62、领先差 0.05，新头像分组阈值 0.62，“疑似”从 0.55 起。依据（只看数字）：

| | 旧参数 | 新参数 |
| --- | --- | --- |
| 用户确认的 U0009 普通样子 vs 变红状态 | 最低 0.46，平均 0.64 | 最低 0.64，平均 0.83 |
| 同一帧主轴格之间（几乎都是不同单位，测试分钟以外两段录像） | 最高 0.65 | 最高 0.57（99% ≤ 0.52） |

参数用 `axis kb settings` 修改，每次修改都记入 changelog。

**知识库 v54 起偏重轮廓**：灰度 0.2 + 边缘 0.8，特征尺寸 40，确定阈值 0.55、领先差 0.05，分组阈值 0.55（“疑似”从 0.48 起）。依据：知识库 54 个用户确认样本（同一单位、同类格）和两段没有重复怪物的录像（测试分钟以外）：

| | 灰度0.4/边缘0.6/32px | 灰度0.2/边缘0.8/40px |
| --- | --- | --- |
| 同一单位，最低的 10% | 0.66 | 0.62 |
| 不同单位最高（知识库 / 录像） | 0.54 / 0.57 | 0.43 / 0.48 |
| 两者间隔 | 0.09 | 0.14 |
| 最近邻判断 | 37/37 | 37/37 |

注意：同一帧里两个相同的怪物（如两只亚婆离召唤物）本来就是同一编号，测“不同单位”时必须排除这种录像，否则会得到 0.99 这样的假高分。

### 临时单位

`axis kb promote <测试目录> --rest provisional` 把这次运行里未核对的临时编号存为“临时”单位（全局编号，`units.txt` 的名称状态列显示“临时（未核对）”，结果里显示“U0030（临时）”），方便在 `samples/U00xx/` 里查看。存入前先用当前知识库识别它的示例帧：大多数与某个临时单位相同就归入那个临时单位；与已确认单位相同只在备注里写“疑似”，不往已确认单位里加未核对的样本。已经转正过的临时编号（见测试目录里的 `promoted_kbv*.txt`）会跳过。

核对临时单位：起名 `axis kb unit rename --id U0030 --name 名称 --name-status confirmed`（或 `--provisional false`）即取消临时标记，其样本改为已确认；是已知单位的用 `axis kb unit merge --from U0030 --into U0003`；不是单位的可改为 `--kind marker`。

**序列稳定判定（识别工具 0.4.0，过渡做法）：** 只看当前格是否连续稳定 0.3 秒，不再要求整条行动轴都不变；否则主轴某一格闪动会让整段行动被漏记。按画面事件计数的正式规则仍待实现。

## 新头像：临时编号与转正

知识库里没有的头像不再写成“未知/待确认”，而是在本次运行内分组并给临时编号（`新01`、`新02`…，按首次出现排序）；同一个临时编号在本次结果里始终指同一单位。分组依据（识别工具 0.2.0）：
1. **外观**：头像与某组的相似度达到 0.72 就并入该组。实测（2026-10-27，测试分钟以外的片段，只看数字）：同一帧里不同单位之间最高约 0.70（95% 低于 0.48）；同一格相邻帧中位数 0.95，但约四分之一因特效、动画降到 0.75 以下。
2. **闪变证据**：同一格在 0.5 秒内出现“A → B → A”（单位不会离开又立刻回来，是特效让头像暂时变样）至少 2 次，A 和 B 合并。
3. **平均相似度合并**：两组的头像平均起来都能互相对上（取较弱的方向）才合并，避免靠一对相似头像把不同单位串在一起。
4. 只出现不到 15 格次（约 1 秒）的组按切换动画等噪声处理，仍记为“未知/待确认”。
5. **轮廓不完整的主轴格不分组**（识别工具 0.3.0；当前格较大、形状不同，不适用）：主轴格边框与行动轴格的吻合度差于 0.9（如被视频字幕遮住、正在切换）时，不参与分组，仍记为“未知/待确认”。实测：被字幕遮住的格中位数 1.10，正常格 0.62。
6. **与已知单位来回切换**：同一格在某个已知单位和一个新组之间来回切换至少 2 次时，注明“疑似 U0007”。这可能是该单位的另一种状态（如加速后变色），也可能是知识库里那个单位的样本有误，由你判断，不自动合并。
7. **当前格与主轴格**：当前格的头像取景与主轴格不同（实测相似度不超过 0.5），同一单位会分成两个临时编号。工具统计“它从主轴第 2 格进入当前格”的次数，过半时注明“疑似与 新02 为同一单位”，由你确认。

拿不准的情况（相似度 0.65 以上但未达到合并条件）只注明“疑似 U0012”或“疑似与 新03 为同一单位”，**不会自动合并**。
- 结果末尾的“[新单位（临时编号）]”列出每组的格次、首次和最后出现的时间；`new_units/` 里有每组的头像截图（`新01_1.png`…）、示例帧和只读的 `new_units.tsv`。

盲测期间知识库不变。你核对后，把结论写成答案文件：

```
新01 = new 昔涟      # 新单位，名称作为注释
新02 = U0012        # 与已知单位相同（旧编号如 CH-爻光 也可以）
新03 = 新01         # 与本次的另一个临时编号相同
新04 = skip         # 不是单位，也不必学习（如盖在行动轴上的视频字幕），不保存
新05 = marker 剩余行动条   # 行动轴上的非单位条目：存入知识库，以后识别出来直接从结果里去掉
```

然后运行 `axis kb promote <测试目录> --answers 答案.txt`：新单位得到下一个全局编号，示例帧存为样本，知识库版本 +1，对照表另存为测试目录里的 `promoted_kbv<版本>_<时间>.txt`；原始结果不变。

## 输出规则

- **孤立截图：** 只列出可见的主轴顺序，第 1 个是当前行动格。右侧待执行的插入行动不列出。当前格是否为插入行动、属于第几次主轴行动，单张截图无法确定，结果中会明说。不做拉条注释。
- **视频或连续截图：** 当前格出现另一个单位、且画面稳定（连续 2 个取样帧相同）时，记一次行动。若该单位在上一稳定画面中位于右侧插入区，则记为插入行动，编号为“主轴序号-插入序号”（如 3-1），不重复记账。序号从第一个稳定画面起算。
- **插入型单位：** 有些单位的行动总是插入回合，例如阿哈时刻，即使它排在主轴里也是如此。用 `axis kb unit rename --id 编号 --insert true` 标记后，它进入当前格时按插入行动编号，离开主轴也不算顺序变化。
- **战斗开始：** 行动轴在至少 2 个取样帧中不存在、随后出现的时刻，视为战斗开始（开场动画结束），序号从这里起算。画面一开始就有行动轴时，注明“未检测到战斗开始”。
- **顺序变化：** 以上一状态推出预期顺序，只在两边都可见的单位之间比较相对次序，记为“顺序变化，原因待确认：某单位相对预期前移/后移 N 格”。仅凭队列无法区分拉条/推条与加速/减速，所以不会直接标“拉条”。
- 不记录单位的出现或消失。

### 建库

```powershell
& $axis kb add-image axis-data\inbox\b1.png --source-type user-screenshot --origin "用户截图 b1" --game-version 4.6
& $axis layout calibrate --image axis-data\inbox\b1.png --id L16x9 --aspect 1.70-1.80 --slot current=x,y,w,h --slot main2=... --slot insert1=...
& $axis layout preview --image axis-data\inbox\b1.png          # 生成标框预览图，用来核对坐标
& $axis kb unit add --kind monster [--name 名称 --name-status candidate --name-source 来源]
& $axis kb unit add --kind character --name 流萤 --name-status confirmed --name-source 用户确认
& $axis kb label S00001 --slot current=CH-流萤 --slot main2=M0001 --label-source user
& $axis kb add-image ... --holdout     # 留出截图：只记正确答案，用 axis kb eval 检验，不进样本
& $axis kb eval
```

### 盲测流程（对应任务要求第 1–5 步）

1. `axis test run --name 名称 <图片…|视频> [--sequence] [--every 秒]`（视频默认每秒 15 帧；稳定判定 0.3 秒，战斗开始前行动轴需消失 1 秒，帧数按取帧间隔换算）：在 `axis-data/runs/<时间>_<名称>/` 中记录本次知识库版本、内容校验值和工具版本（`meta.txt`），复制输入图片，然后运行工具。
2. 工具首次输出写入 `raw_result.txt`（与逐格明细 `raw_detail.tsv` 一起设为只读），之后不再改动。
3. 把 `raw_result.txt` 交给你，等你告知正确答案。这一步 Claude 不看图补答案。
4. 把你的纠正写成答案文件，例如：
   ```
   [b1.png]
   current = CH-流萤
   main3 = M0004
   ```
   视频帧写成 `[录像.mp4@12.5]`。然后运行 `axis test correct <测试目录> --answers 答案.txt`：原截图（或该视频帧）、裁剪头像和正确标签进入知识库，误识别记入 `corrections.log`，知识库版本 +1；随后重新识别，另存为 `corrected_kbv<版本>_<时间>.txt`。
5. 视频无法解码或没有适用布局时，结果中会写“未完成”。这种情况不会用人工看图代替工具结果。
6. 转正临时编号（`axis kb promote`）后，用 `axis test rerun <测试目录>` 以当前知识库重跑同一段，另存为 `corrected_kbv<版本>_<时间>.txt`。
7. 纠正时取帧要取在行动中段：结果里每条行动的时间比它真正开始晚约 0.3 秒（稳定判定）。样本归错单位时用 `axis kb relabel --sample A000123 --unit U0002 --reason …` 改归。

录制器从视频中途开始录时（`recording_info.txt` 写有“文件时间 0 对应视频 01:09”），结果里的时间自动换算为视频时间；`raw_detail.tsv` 和纠正答案里的帧时间仍是录像文件时间。

### 从 B 站链接录制

```powershell
& $axis record "https://www.bilibili.com/video/BV…/" --start 1:20 --end 2:30 [--out 目录]
```

- 在录制窗口里播放（静音、关闭并隐藏弹幕、选当前账号可用的最高清晰度；用户在启动器视频页“登录 B 站…”登录过录制器自己的浏览器后，`axis record` 也会用这个登录），按视频时间截取画面，写成 `recording.avi`（Motion-JPEG，15 帧/秒，文件时间 0 = 起点）和 `recording_info.txt`（链接、标题、UP 主、页面转载声明、访问时间、清晰度、实际区间、sha256）。默认保存到 `axis-data/recordings/`。
- 要求登录、人机验证、黑屏（受保护视频）、找不到播放器、长时间不播放时停止并说明原因，不绕过。
- 录制窗口放在所有屏幕左侧之外，不显示、不抢前台、不进任务栏；浏览器参数关闭了“被遮挡窗口停止绘制”，所以视频照常渲染（实测 30 张抽样帧全部不同）。
- 播放器先用自己的“网页全屏”铺满录制窗口（按钮无效时用样式表把播放器固定到窗口），窗口按视频原始清晰度调整（最大为主屏幕大小）。截图位置不可信（超出截图或不是视频的宽高比）的帧会丢弃并计数，`recording_info.txt` 里记录窗口、视口、缩放和画面区域，便于排查。
- 开始录制前暂停在起点试截几张：PNG（无损）每步不超过 60 ms 就用 PNG，否则用 JPEG（WebView2 内置质量）；再按每步耗时算出播放速度（0.05 一档，最低 0.15×），保证每秒视频截满 15 帧；录制中每 20 次截取检查一次，不够就再放慢。实测 1080P：PNG 约 400 ms、JPEG 约 70 ms，播放 0.55×，每秒视频截取 14.8 次。
- 实测（2026-10-27）：B 站未登录只开放 360P，登录后可到 1080P（60 帧需大会员）。360P 下现有行动轴检测尚未验证，需要在第 4 步（识别器与清晰度门槛实验）里处理。
- 启动器的“视频”页用同一个录制核心；建库和盲测仍在这里用 `axis` 完成。

不能或不该录制的视频，用 `axis kb add-link` 只记录链接、标题、UP 主、页面声明和访问时间，记录保存在 `kb/web_links.json`。

### 画面线索（凹分检定第 3 步）

规则和线索的样子见 [score-retry-check.md](score-retry-check.md)。读取方法（`src/AxisRecognizer.Core/ScreenCues.cs`，不调用大模型）：

| 线索 | 读法 | 开放视频上的结果（2026-10-28） |
| --- | --- | --- |
| 当前格左侧标记 `marker` | 在当前格左边缺口处取约 3.4 倍缺口半径的方块；按颜色分出亮青色（我方）和亮红色（敌方）像素；形状与样本比对，同时用中心色块面积独立判断（圆点小、菱形中、四角星大），两者一致才给标签 | 用铁墓、绘世的 43 个样本，在没见过的亚婆离 0–3 分钟上：有标签的约 340 帧里约 1% 读错，都是单独一帧（淡入中的四角星、一帧红点读成菱形），由第 5 步的“连续几帧一致”过滤 |
| 右下角状态文字 `phase-text` | 整个框判断有没有文字；"我方"/"敌方"只看前两个字，用模板在 ±几像素内滑动匹配（细笔画对 1–2 像素的偏移很敏感，直接比对会两边都像） | 亚婆离 10–40 秒：我方、敌方全部读对，没有读错的帧 |
| 战斗开始 | 整个画面除中间一行外都是黑的，中间一行大部分是白色 | 三个视频各找到一次（7–8 秒处约 0.5 秒），9 分钟里没有误报 |
| 选招按钮（招式） | 在右下角按钮区找圆形按钮（霍夫圆），只认三个已知位置：普攻（约 1.525, 0.853）、战技（约 1.677, 0.770）、单按钮（约 1.607, 0.853，例如忆灵回合）；两个按钮里放大的那个（半径约 0.070 对 0.050）就是选中的。不看按键标记和角色图标，所以键鼠和手柄通用 | 绘世 0–3 分钟：读到的普攻、战技、单按钮与画面一致；按钮淡入中的帧不给结果；亚婆离（键鼠 Q/E）和铁墓（手柄 X/Y）按钮位置相同 |
| 横幅文字 `banner` | "战斗开始"（每一波开始，多波时是"战斗开始 x/n"）和"结束战斗"在画面上方中间；结算的"挑战成功"在稍下方（上面还有模式小标题）。用样本里的四个字做模板，在对应的横条里滑动匹配，并给出文字中心：有"x/n"时同样四个字会偏左（中心约 0.842，单波次居中约 0.889） | 绘世第 1 波（0:08–0:10）和第 2 波（3:07.8–3:09.2）都找到，得分 0.75–0.90；亚婆离 3:00–6:00 没有误报。"结束战斗""挑战成功"各只有铁墓 1 个样本，还需要别的视频检验 |
| boss 阶段点 | boss 头像右边、血条上方的一排小点，亮的（白心红光）是剩余阶段，用过的变成暗圈。数亮点：大小约 0.007 画面高的实心圆斑、在点所在的那一行、从头像右边开始间距约 0.016 连成一串（红光在红色战场上分不出来，所以不靠它） | 绘世 7:02.5 从 2 变 1（用户给出的转阶段 7:00–7:05）；铁墓 0–3 分钟一直是 3；被动画挡住时读 0 |
| 轮次和剩余行动值 `av-bar`（第 4 步） | 行动轴下方"⌛2 \| 194"这一条的位置随格数变化，用样本条左端（左圆头和沙漏）在行动轴一列里找；再把沙漏右边的白色字切成单个字符（"\|"是很细的竖线，按宽高比认），每个数字和样本里学到的字形比对。样本标签就是读数，例如 `2\|194`，一个样本能教会其中的每个数字。某个数字的匹配不到 0.8 时整条读数作废（宁可"看不清"，不给错数） | 用绘世 10 个样本（数字 0–9 都有）：铁墓 0–3 分钟读出"2\|282"等，亚婆离"2\|241""2\|213"，绘世 3:00–6:00 从 190 一路降到 87，人工抽查全部正确；留出的"2\|157"也读对。0、5、7 补样本前会被读错（得分 0.67–0.72），所以设了 0.8 的门槛 |
| 回合开始白闪 | 当前格内部的平均饱和度：平时约 80–90，白闪时降到 15–35、亮度升高，持续约 0.1–0.2 秒。白闪时当前格边框常常认不出，所以在最近一次找到的位置测量 | 只输出数值，判断放在第 5 步 |

```powershell
& $axis cue add 录像.avi --at 41,61.5 --cue marker --label ally-extra [--label-source claude-assisted|user] [--notes 备注]
& $axis cue relabel --id C000047 --label none --reason 依据
& $axis cue list [--geometry 1]
& $axis cue scan 录像.avi --start 0 --end 180 --every 0.25 [--sheet 标记拼图.jpg] [--probe 目录]
& $axis video sheet 录像.avi --out 拼图.jpg --crop 0.8,0.82,0.2,0.14 --every 0.5 --start 10 --end 40
```

现有线索样本都由 Claude 从三个开放视频逐帧核对后标注（`claude-assisted`），需要你抽查确认。取错的样本用 `axis cue exclude` 停用（文件保留，记入 changelog），例如自动定位找错位置的 C000065。

速度（Debug 版，1080p，`axis cue scan` 末行会打印）：行动轴头像每帧平均约 74 ms、最长约 140 ms；画面线索每帧平均约 94 ms、最长约 175 ms。在 1 秒内出判定没有问题，但实时截图时不能每秒处理 15 帧，第 6 步再按需要精简。
